## Shell call timeout badge

`lib/duration-format.ts` labels a whole number of seconds as `57s` / `1m 30s` / `2m` / `1h 5m`, plus `remainingTimeoutSeconds` clamped to `[0, timeout]`; `lib/tool-names.ts` adds `isShellToolName` and `getShellTimeout`. `components/ShellTimeoutBadge.tsx` counts the time a running `bash` / `powershell` call has left before its `timeout`, in the slot that later holds the elapsed duration, and `ToolCallBlock` in the upstream-synced `components/MessageView.tsx` only passes it that call's start time (the assistant message's `timestamp`, via `BlockView`) and keeps the elapsed-duration rendering.

The badge is fork-only and lives in its own file so `MessageView.tsx` gains no state, effect or interval — the countdown's 1s tick is there, stopped once it reaches 0. Pi streams a running shell tool's output as a partial result that carries no timestamp, and the elapsed duration is derived from that timestamp, so `!result?.timestamp` is what marks the call unfinished (upstream renders that duration as a plain `{duration}s`). The countdown starts from the message timestamp rather than the tool's real start, so it can reach 0 a few seconds before pi kills the command, which is why the zero state is the `chat.toolTimeoutEnding` key (`terminating soon` / `即将终止` / `即將終止`) in all three locales instead of a `0s`; the running value itself carries no words — `chat.toolTimeout` is gone. Badge text is the card's warning red (`#f87171`, the same colour an erroring tool name gets) in every state: the countdown, the full limit shown while the message still streams, and the zero state.

## Default directory and the New project layer

"Use default directory" is upstream #996 and stays byte-identical to it: `lib/default-cwd.ts` (`localDateStamp`, `defaultCwdPath`, `~/pi-cwd/<YYYYMMDD>`), a POST-only `/api/default-cwd`, and no default-cwd entry in the file allow-list. Do not add a configurable default cwd back: upstream **closed** #892 on 2026-09-29 in favour of #996's design, where a dated folder keeps a first-time user out of their own data and needs no stable path because any folder with a session reopens from the picker.

Our own "New project" action is a separate layer instead: `lib/default-project.ts` reads `defaultProjectPath` from `~/.pi/agent/pi-web.json` (empty = the built-in `~/pi-cwd`, upstream's dated-folder parent), `GET`/`PUT /api/default-project` own that setting, and `POST /api/default-project { name }` creates or reuses `<project directory>/<name>`. The sidebar's New project dialog submits the name and then selects the returned path through `commitCustomPath`, so `/api/cwd/validate` still owns validation, project identity and the allow-list. Keeping this route apart from `/api/default-cwd` is deliberate — it is what makes syncing upstream's default-cwd code conflict-free.

## ntfy notifications (`lib/ntfy.ts`)

The two upstream completion notifications are browser-bound: `lib/web-push.ts` needs a registered push subscription and `lib/browser-notifications.ts` needs the Notification permission and a hidden window, which is a high bar on a phone. `lib/ntfy.ts` adds a server-side runner instead: the user writes one `curl` command with `{{…}}` placeholders, and when a top-level session finishes Pi Web substitutes them and runs the command, so a phone subscribed to the resulting ntfy topic gets the message — no browser permission, no open window, no service worker.

Run, not interpret: `splitShellWords()` (upstream's `lib/shell-words.ts`, which already refuses pipes, `&&`, redirects and `$(…)`) turns the command into an argv list, the `{{…}}` substitution happens **after** the split so a title with spaces or quotes stays one argv word, and the first word must be `curl`. The process then runs with no shell and a timeout; a failure is logged as an exit code only, so a token in the command never reaches a log. The setting is deliberately just two fields — `enabled` and `command` — in the fork's own `~/.pi/agent/pi-web.json` under `ntfy`, written with the same read-modify-write as `defaultProjectPath`. `GET`/`PUT /api/ntfy` read and write it and `POST /api/ntfy` runs the stored command once with test values. Settings › General renders a command box, a row of tappable `{{…}}` chips, and a collapsible help that lists the placeholders and ready-made commands; on a wide panel the help sits beside the command, on a phone it stacks below (and the settings modal follows `--app-viewport-height`, so the keyboard does not cover the buttons). `lib/ntfy-templates.ts` (kept client-safe so the browser bundle never pulls in `node:child_process`) exports `NTFY_VARIABLES` and `NTFY_COMMAND_EXAMPLES`, which the chips, the help and the unit test all read, so the help cannot drift from the code. `{{url}}` comes from the optional `PI_WEB_PUBLIC_URL` environment variable. The trigger is one call next to upstream's push call in `lib/rpc-manager.ts`'s `onAgentRunComplete` — an upstream file, so the diff stays at one import and one call.

## Slash-command favorites (`lib/slash-command-favorites.ts`)

The `/` palette lets a card be marked with a top-right ★/☆ toggle, and a `+` button between the image and model controls opens a panel of the marked commands. The panel shows **command names only** (no descriptions) and clicking a row sends that command at once. Marks are keyed by command name alone — not by source — so one name covers the same command across the builtin, extension, prompt and skill palettes, and the stored value is a plain `string[]` in the fork's `~/.pi/agent/pi-web.json` under `slashCommandFavorites`.

`lib/slash-command-favorites.ts` owns `normalizeSlashCommandFavorites` (strings only, trimmed, a leading `/` stripped, deduped first-seen, capped at `MAX_SLASH_COMMAND_FAVORITES = 100` so a hand-edited file cannot bloat the panel), `readSlashCommandFavorites` and `writeSlashCommandFavorites` (read-modify-write that keeps unrelated fields, drops the key when the list empties, and creates nothing for an empty list on a missing file). `GET`/`PUT /api/slash-command-favorites` in `app/api/slash-command-favorites/route.ts` guards with `isApiRequestAllowed` / `hasJsonContentType`, like `/api/ntfy`. `lib/slash-command-favorites.test.mjs` pins normalization, the cap, the read-modify-write and the damaged-file refusal.

In `components/ChatInput.tsx` the list loads once on mount (failures leave it empty), a star click toggles the mark optimistically and rolls the whole list back if the `PUT` fails, the palette card is wrapped in a `position: relative` div (a nested `<button>` is invalid) so the star can sit absolutely over it, and `handleSend` gained an optional `override` argument — a quick-pick row calls `handleSend("/name")`, which sends that exact command without clearing or reading the draft already in the input. The `favoritesMenuRef` click-outside effect mirrors `controlsMenuRef`. The four `chat.slashFavorite*` keys are in all three locales. Upstream has no per-card marking and no quick-pick, so this is fork-only.

## Explorer "show ignored files" toggle

Upstream's file tree always drops `.gitignore`d and conventionally hidden entries. The explorer toolbar's third button (an eye, after new file / new folder) toggles a show-all listing: `FileTreeVisibilityOptions.includeIgnored` in `lib/file-tree-visibility.ts` returns `(name) => !ALWAYS_HIDDEN_NAMES.has(name)` before any Git call, so the listing stays one `readdir` and only `.git` / `.DS_Store` stay hidden. `components/FileExplorer.tsx` threads `includeIgnored` into `fetchEntries`, both `TreeNode` instances and the fetch effects' dependency lists, so a toggle re-lists every open directory. Access rules are untouched — the parameter changes visibility only, and `/api/file-index` (`isHiddenOutsideGit`) still hides ignored files from the `@`-mention list.

The preference is per browser, beside upstream's explorer-open state: `EXPLORER_SHOW_IGNORED_STORAGE_KEY = "pi-web:file-explorer:show-ignored"` with `loadExplorerShowIgnored` (a missing key means the new default, `true`) and `saveExplorerShowIgnored` in `lib/file-explorer-state.ts`. The component seeds `true` and hydrates after mount so the first client render matches the server's; the button is tinted while on and swaps between the eye and the eye-off icon. `files.showIgnoredFiles` / `files.hideIgnoredFiles` are in all three locales.

## Active project tabs

Parallel agents are the normal case: several projects can hold a running agent, or a finished run the user has not opened yet, at the same time. The sidebar's project dropdown already counted that activity (`getProjectActivity`), but seeing it meant opening the sidebar. The main top bar now renders one tab per project, running ones first, immediately left of the file-panel toggle — which is why that toggle narrowed from 36px to 28px (`FILE_PANEL_TOGGLE_SIZE` in `components/AppShell.tsx`; `TOP_BAR_ICON_BUTTON_SIZE` stays 36 for the remaining top-bar buttons).

`getProjectTabs()` in `lib/project-groups.ts` is the whole selector: `getRecentProjects()` (newest activity first, one row per stable project key) is stable-sorted by rank — a project with a running agent first, then one with an unread completion, then an idle project — and sliced to `Math.max(MIN_PROJECT_TABS, busy)`, so recency survives inside a rank and every busy project stays in the strip while idle projects top the list up to `MIN_PROJECT_TABS = 3`. That is why the strip almost always renders something: only a user with fewer than three projects, or none at all, sees fewer than three tabs. Clicking a tab calls the existing `handleCwdChange(project.root, project.root, project.key)`, so a switch behaves exactly like picking the project in the sidebar, `restoreWorkspaceContext` included; the current project's tab is marked `data-project-tab-current` / `aria-current` and does nothing when clicked. When the strip does render nothing the toggle takes back the right-aligned `auto` margin it always had. Each tab carries the project panel's own badge: `showProjectActivity` is exported from `components/SessionSidebar.tsx` and called with the `getProjectActivity` map plus a `compact` flag, which keeps only the spinning ring — so the 32px mobile chips show the same ring the sidebar dropdown shows without its counts.

`unreadSessionIds` is owned by `SessionSidebar`'s poll (localStorage `pi-web:unread-session-ids`), so the sidebar reports it upward through `onUnreadSessionIdsChange`, mirroring the existing `onRunningSessionIdsChange`. Mobile chips show one uppercase initial (`Array.from(name)[0]`) and the strip hides together with the toggle under the narrow-mobile `.more` action layer. `components/AppShell.active-projects.test.mjs` pins the wiring and `lib/project-groups.test.mjs` the selector.

## Bun terminal backend (bun-pty)

Bun cannot drive node-pty: the PTY exits immediately with code 1 and emits zero bytes, so the terminal tab stayed dead under `dev:bun` / `start:bun`. `lib/terminal-pty.ts` isolates the choice — `isBunRuntime()` reads a `Bun` global, `ptyModuleName(inBun, override)` returns `"bun-pty"` under Bun and `"node-pty"` under Node, `PI_WEB_TERMINAL_BACKEND=node-pty|bun-pty` overrides the guess (any other value means auto), and `loadPtyModule()` requires the chosen module inside `createTerminal`, so a native-load failure still reaches the API's JSON error path. `lib/terminal-manager.ts` only calls `loadPtyModule()`; nothing else in it changed, which keeps the upstream file's diff to an import plus that two-line load.

Both modules expose the same `spawn(file, args, options)` → `IPty` shape, so `PtyModule` / `PtySpawnOptions` structural types stand in for node-pty's own types and the adapter imports `IPty` as a type only. The two differ where it matters: bun-pty's `kill()` ignores the signal and fires `onExit` synchronously, so `killTerminal`'s SIGKILL escalation after two seconds is a second SIGTERM — harmless, because the process is already gone.

bun-pty goes in `optionalDependencies` (pinned `0.4.11`). It cannot go in `serverExternalPackages`: that list only externalizes `.mjs`, `.cjs`, `.js`, `.json` and `.node` entries, and bun-pty's package entry is a `.ts` file. Bundling it fails too — it imports `bun:ffi` and `dlopen`s a native library resolved at runtime, and Turbopack resolves even a literal `createRequire` specifier (`⨯ ./node_modules/bun-pty/src/index.ts` / `Error: Unknown module type` 500s every route). An `import`/`require` of `node:module` is not the way out either: in a production build the bundler swaps it for a module-map emulation that only resolves modules already in the graph, so `createRequire(__filename)("bun-pty")` works under `next dev` and then throws `Cannot find module 'bun-pty'` when `bin/pi-web.js` serves the `build:bun` output. `loadBunPty()` therefore takes the real `createRequire` from `process.getBuiltinModule("module")` — an ordinary property read no bundler rewrites — and resolves from `__filename` (the emitted server chunk), falling back to `process.cwd()` (the package directory `bin/pi-web.js` spawns `next start` in), so no static request naming bun-pty ever reaches a bundler. The prebuilt `librust_pty` shared library ships inside the tarball; `BUN_PTY_LIB` points at it when a platform build is missing, and `lib/terminal-pty.ts` names that variable — with the `bun add bun-pty` / `npm install bun-pty` fallback — in the error a failed load throws. `lib/terminal-pty.test.mjs` pins the selector; `e2e/terminal-bun.mjs` runs the whole terminal against a Bun dev server and asserts a real shell echo, exit code and close.

## Theme palettes and the derived dark list (`lib/theme.ts`)

Upstream names the dark palettes twice inside one file: `isDarkTheme()` compares `theme === "dark" || theme === "pine"`, and the injected `THEME_INIT_SCRIPT` repeats the same pair in its `r.classList.toggle("dark", ...)`. The fork makes the option list the single source instead. Every `THEME_OPTIONS` entry carries `resolvesTo: "light" | "dark" | "system"` — `"system"` being `auto`, which follows the OS scheme rather than naming a palette — and the tuple is pinned with `as const satisfies readonly ThemeOption[]`, so a new palette that omits the field fails `tsc` (TS2741) instead of silently rendering as light. `DARK_THEME_IDS: readonly ResolvedTheme[]` is filtered out of that list, and both `isDarkTheme()` and the first-paint script read it, so the script's toggle is generated (`r.classList.toggle("dark",["dark","pine"].includes(t))`) and the two can no longer drift; the emitted string is unchanged for the six current palettes.

A sync has to fold upstream's hardcoded pair back into the derived list rather than keep both: a palette that is dark in `THEME_OPTIONS` but missing from the script's list flashes light on the first paint, because the inline script sets `class="dark"` before hydration, and it is the class — not `data-theme` — that drives `globals.css`'s three `html.dark` rules (the Catppuccin file icons and the web-login error). Adding a palette stays four edits: the entry, its `[data-theme="…"]` block in `app/globals.css`, an SVG branch in `components/ThemeIcon.tsx` and a `settings.theme*` label in the three locales. `lib/theme.test.mjs` already loops over every `THEME_OPTIONS` id and compares the script's `html.dark` against `isDarkTheme()`, so it fails on a script left holding a stale list.

A sync will also bring back the dead top-bar theme menu: `e2e/themes.mjs`'s second half — the `Theme: …` button, the `Appearance` menu, its `menuitemradio` / Escape / dismissal / focus checks and its 1440px "dark tokens stay neutral gray" assertions — and the three locales' `theme.*` labels (`Theme: Light` … `Theme: System`) were removed here, because that UI no longer exists in this checkout (the Settings radio group is the live selector) and the second half could only time out. Delete them again after a sync. Note that the neutral-gray check has no replacement, so `dark`'s greys are not checked for a colour cast anywhere.


## Thinking block

Upstream's `ThinkingBlock` (`components/MessageView.tsx`, an upstream-synced file) is one `<button>` holding a bulb icon and the collapsed first-line preview, with the duration label as a sibling *outside* the button, and its expanded body as a flex sibling to the icon's right. Upstream dropped the visible title when it simplified the thinking controls. The fork keeps a handful of deviations in that one component, plus a height cap:

- **Bold title.** `{t("i18n.thinking")}` renders next to the bulb as `<span style={{ flexShrink: 0, fontWeight: 600, flexGrow: expanded ? 1 : 0 }}>`, so the block reads as a titled card again.
- **The whole header line is the toggle.** Upstream's button is icon-width when expanded (`width: expanded ? 14 : "100%"`), so an expanded block could only be collapsed by hitting the bulb. The duration label moved *inside* the button here, making one full-width click target — the same interaction as `ToolCallBlock`'s header. The duration still sits at the right edge of the line in both states: collapsed the preview span carries `flex: 1` and pushes it there; expanded there is no preview, so the title takes `flexGrow: expanded ? 1 : 0`. (The tool card keeps a preview rendered in both states, which is what pushes *its* duration right.)
- **The expanded body sits below the header, not beside it.** The card is a `flexDirection: "column"` box: a header row holding that single full-width button, and under it the body once expanded. Beside the header the body's left edge was pushed right by the icon and title, leaving a blank strip under them along every wrapped line.
- **The body follows the tail while the model streams.** With the cap in place the growing text became the block's own scroll region, so new lines landed below the fold and only a manual scroll revealed them. The expanded body is therefore `components/ThinkingBody.tsx`, a fork-only component the body `div` moved into (class and inline styles unchanged): it mounts on expand, so opening a running block jumps straight to the newest text, and on every streaming render it sets `scrollTop = scrollHeight` — but only while the reader is still at the tail, decided by lib's tested `getLiveFollowAttached` (the same call `ChatWindow` makes for the chat scroller), which detaches on a real upward scroll and re-attaches near the tail. A bare `isScrollAtTail` test was tried first and was wrong: the browser nudges `scrollTop` a few pixels when the growing content first overflows the cap, and one fast chunk can land a paragraph below the effect's own scroll to the tail, so it read the streaming block as "the reader scrolled away" and stayed silent for the rest of the thinking phase. Scrolling up still detaches the follow and returning to the bottom re-attaches it; the element unmounts on collapse, so a detached state does not survive. `MessageView.tsx` gains only the import, `<ThinkingBody follow={isStreaming === true} color={…}>` and the `isStreaming` prop `BlockView` already had in hand for `TextBlock` — no state or effect in the upstream file.
- **The reader's expansion outlives the block's remounts.** Upstream keeps it in a plain `useState(isThinkingExpandedByDefault)`, but a streaming assistant message is rendered from `streamState`, re-rendered from `messages` after `message_end`, and re-keyed twice — the message wrapper once `entryIds` arrive from the session file, and the block itself, which `MessageView` keys on `entryId ?? "stream"`. Each hop remounts `ThinkingBlock`, so expanding a running block collapsed it seconds later. The fork records the reader's own choice in `lib/thinking-expansion-state.ts` and seeds the state from it — the trick upstream already uses for tool cards in `lib/tool-call-expansion.ts`. A tool call has a stable `toolCallId` to key on; a thinking block has no id of its own and the streaming render is given neither a session id nor an entry id, so the decision is keyed by the block's index inside its message and guarded by the block's own text opening — its first line, the shape `getThinkingPreview` gives a committed block (`lib/message-display.ts`), because `lib/session-reader.ts` replaces a saved block's text with exactly that preview. A raw-text guard (first 32 characters of the trimmed text) was tried first and stopped matching the moment the turn was saved, so the block collapsed again as the answer arrived. That one block's growing text always keeps that opening, while another message's block at the same index starts differently. An empty block records nothing, because an empty opening would match every later block at that index.
- **The turn's process section stays open for that reader.** The block-level memory is only half of it. `ProcessDetailsGroup` lives in the upstream-synced `components/ChatWindow.tsx` (~line 185) and is re-keyed on answer availability — `key={finalAnswerMessage ? "answered" : "unanswered"}` with `defaultExpanded={!finalAnswerMessage}`, deliberately, so a turn first rendered without an answer does not stay open once the answer shows up. The moment the turn gets its answer the whole section therefore remounts *collapsed* and an opened card leaves the DOM outright. `ChatWindow` therefore asks `hasOpenedThinking(finalProcessBlocks)` and hands the answer to the group as its own `rememberedOpen` prop, which `ProcessDetailsGroup` turns into an open section from a `useLayoutEffect` of its own. Upstream's `defaultExpanded={!finalAnswerMessage}` and its `key={finalAnswerMessage ? "answered" : "unanswered"}` are left byte-identical, because upstream's `components/ChatWindow.process-details.test.mjs` pins both by source regex; only the initial state follows the memory, so a manual collapse of the section still sticks. That import, the `openedProcess` const and that one prop are the only render-path changes this feature needs.

A long expanded body also used to grow without bound and push the rest of the chat off screen. It is capped at half the screen on desktop and a third on phones (the same `(max-width: 640px)` breakpoint as `hooks/useIsMobile.ts`). The rule is `.thinking-block-content` in `app/globals.css` — `max-height: calc(50dvh - 14px)`, `overflow-y: auto`, `overflow-x: hidden`, `overscroll-behavior: contain`, `scrollbar-gutter: stable` (the same scroll conventions as `.extension-widget-panels`), overridden to `calc(33.3333dvh - 14px)` under the phone media query. The 14px subtraction is the card's own 6px top/bottom padding plus its 1px borders, so the whole card — not just its text — stays within the screen fraction.

The cap is one `className` in `app/globals.css`; the rest is style objects and one `isStreaming` prop in the upstream-synced `components/MessageView.tsx`, plus the fork-only `components/ThinkingBody.tsx` and `lib/thinking-expansion-state.ts`, and the `openedProcess` half in the upstream-synced `components/ChatWindow.tsx`. The deferred/loading content fetch and the bulb's active colour are upstream's; the expand/collapse state is upstream's too, the fork only seeds it from the remembered choice and records the reader's own toggle. `components/ThinkingBody.test.mjs` pins the class, the `getLiveFollowAttached` call and the `isStreaming` wiring, and `lib/thinking-expansion-state.test.mjs` pins the remembered expansion; the title, the click target and the body placement are pinned by nothing — a sync that brings upstream's `ThinkingBlock` back will silently drop the title, shrink the click target to the icon again and return the body to the icon's right, so re-apply from this note.
